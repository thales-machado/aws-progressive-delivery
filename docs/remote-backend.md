# Remote backends

Two Terraform states are involved and both can live in the same backend:

| State | Owner | Key |
| --- | --- | --- |
| API, deployment, stage | You, applied outside the pipeline (local, Atlantis, CI) | your choice |
| Alarms | The pipeline | `<keyPrefix>/<apiId>/<stage>/monitor.tfstate` |

## S3

```hcl
terraform {
  backend "s3" {
    bucket       = "my-terraform-state"
    key          = "apigw-basic/terraform.tfstate"
    region       = "us-east-1"
    encrypt      = true
    use_lockfile = true
  }
}
```

`use_lockfile` needs Terraform 1.10 or newer. On older versions use a DynamoDB table (`dynamodb_table`) instead. The example file is
`examples/apigw-basic/backend.tf.example`. For the pipeline, pass the same bucket:

```groovy
monitor: [backend: [type: 's3', config: [bucket: 'my-terraform-state', region: 'us-east-1', use_lockfile: 'true'], keyPrefix: 'aws-progressive-delivery']]
```

`config` entries become `-backend-config=key=value`. `configFile` adds `-backend-config=<file>` as well. The state `key` is always
generated by the library.

## Local

`monitor.backend.type: 'local'` keeps alarm state in the job workspace (`.progressive-delivery/<apiId>-<stage>`). It only works while
the same workspace serves `START`, `CONTINUE` and the final destroy, so use it for sandboxes.

## Cloudflare R2

R2 speaks the S3 API, so the `s3` backend works with these settings:

```hcl
backend "s3" {
  bucket                      = "tfstate"
  key                         = "apigw-basic/terraform.tfstate"
  region                      = "auto"
  endpoints                   = { s3 = "https://<account-id>.r2.cloudflarestorage.com" }
  skip_credentials_validation = true
  skip_region_validation      = true
  skip_requesting_account_id  = true
  skip_metadata_api_check     = true
  skip_s3_checksum            = true
  use_path_style              = true
}
```

Whether `use_lockfile` works on R2 has not been verified here. Without locking, serialise runs yourself; the Jenkinsfile already uses
`disableConcurrentBuilds()`. R2 needs its own access keys in the environment (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`), which
conflicts with using AWS credentials for the same run, so prefer S3 when the pipeline also calls AWS.
